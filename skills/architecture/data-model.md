# Data model

## Core entities

- `institutions`: organisation and configuration.
- `users`: authentication identity mapped to an institution membership and role (`admin`, `teacher`, `student`). Student usernames are generated by default but editable; email supports reset and may be school-provided or student-added/verified at first login.
- `teachers`, `students`: institution-owned profiles; student holds identifier, optional roll number, phone/WhatsApp/email, profile photo reference, and status.
- `student_field_definitions`: institution-wide configurable student-form fields, ownership (`school` or `student`), requiredness, type, and active status. Core identity/relationship fields remain protected system fields.
- `groups`, `group_memberships`: general terms for batch/class/section and reusable sub-batches with date-effective membership.
- `teacher_assignments`: school-controlled teacher + batch/sub-batch + course authorisation. It permits corresponding extra classes but is separate from timetable slots.
- `courses`: optional institution-owned subject/course.
- `schedule_templates`: weekly recurrence definition, teacher, group/course, local time, and active range.
- `lectures`: real dated occurrences, with scheduled/original times, selected audience mode, status, and source template where applicable.
- `lecture_students`: snapshot/custom selection of expected students. A lecture must preserve its intended audience even if group membership later changes; teacher additions are marked `temporary` or `manual` and do not create permanent students automatically.
- `attendance_sessions`, `attendance_entries`: capture/review event and one final status per expected student.
- `face_enrolments`: private-object reference, embedding reference/version, quality/status, consent record, timestamps, and match-to-existing-enrolment result. One approved enrolment is selected as profile photo.
- `temporary_attendees`: name, batch, roll number or teacher-created temporary reference, originating lecture, and reconciliation status. School can link it to a newly created student and migrate prior attendance.
- `attendance_audit_events`: suggestions, human overrides, actor, timestamp, and reason when required.

## Key rules

Schedules are templates; lectures are occurrences. Reschedule/cancel affects a lecture occurrence, not history or the template unless explicitly requested. Extra lectures have no template source. A custom lecture must create `lecture_students`; whole-group lectures should snapshot eligible students at creation/start time using a documented rule.

Store timestamps in UTC and each institution's IANA timezone separately. Use UUIDs, foreign keys, uniqueness constraints scoped by institution, and soft/status-based retirement where history matters. Record all attendance/schedule edits with actor, time, prior value, and changed value.
